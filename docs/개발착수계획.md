# 착공계·공정표·인원장비투입계획 자동화 개발 착수 계획 v0.1

- 작성일: 2026-10-17
- 기준 문서: `착공계·공정표·인원장비투입계획 자동화 SRS v1.0.md` (요구사항 SR 116개, 시험 T-01~T-45), PRD v0.1, VPS
- 일정은 **최단 기준 추정**이다. 기술 스택, 베타 업체는 아직 확정되지 않아 가정으로 적었고, 9장에서 확정할 것을 모았다.
- **올케어솔루션·올케어안전플랫폼과 무관한 별도 서비스로 만든다.** 올케어솔루션 홈페이지에는 '착공계 작성' 메뉴(링크)만 달며, 이 작업은 홈페이지 쪽에서 1차 출시 뒤에 하고 8주 일정에 포함하지 않는다(11장).
- **범위는 줄이지 않았다.** SRS의 SR 116개를 모두 1차에 만든다. 일정은 순서를 바꾸고(베타를 앞당기고, 용역비·대시보드를 베타와 병행) 겹쳐서 줄였다.

## 2. 일정을 줄인 방법

| 방법 | 이전 계획 | 이번 계획 |
| --- | --- | --- |
| 베타를 앞당긴다 | 모든 기능이 끝난 뒤 베타 | 계산·서류·출력·관리자 로그인·보안 핵심이 끝나면 바로 베타. 용역비·대시보드는 베타와 병행 |
| 베타 기간 | 3주 | 2주(실제 업체 1건 작성·납품·보완) |
| 준비 기간 | 1주 | 3일(스택 확인, API 시험, 시험 데이터, 시험 틀) |
| 보안·품질 보강 | 마지막에 2주 | 개인정보 암호화·마스킹·권한은 베타 전(5주차)에 넣고, 알림·수치 검증은 베타 중에 한다 |
| 작업 중첩 | 순차 | 입력·계산 코어와 서류·출력은 겹쳐 진행, 용역비는 베타와 병행 |
| 계산 로직 | 새로 설계 | 엑셀 시제품 계산식을 옮기고 기준값으로 검증 |

보안의 핵심(SR-NF-12~18)을 베타 전에 두는 것은 줄이지 않는다. 베타에서 업체의 실제 주민등록번호·계좌번호를 다루기 때문이다.

## 7. 일정이 밀릴 때

범위를 줄이는 순서다. 위에서부터 먼저 미룬다.

1. 알림 항목 일부(SR-NF-27~31)를 출시 직후로 미룬다.
2. 대시보드의 운영 지표(SR-ADM-02, 03)를 최소 표시로 줄인다.
3. 건축·토목·조경·전기 공종 기준 데이터 확보는 베타 뒤에 둔다(PRD 부록 4에서 이미 순차 오픈).
4. 그래도 부족하면 베타 기간을 1주로 줄이고 판정 근거를 1건으로 제한한다.

계산 코어, 서류 생성, 검증, 출력, 보안 핵심은 줄이지 않는다. 이 중 하나라도 빠지면 제품이 성립하지 않는다.

## 8. 범위 관리 원칙

- 1차 범위는 SRS의 SR 116개이며, 2차·3차 항목(한글 금액 표기, 문서번호 자동 부여, 선후행 일정, S-curve 등)은 구현하지 않는다.
- 요구가 바뀌면 PRD → SRS → 이 계획 순으로 고치고, 시험 번호와 SR 번호를 함께 갱신한다.

| 3 | 베타 업체와 일정 | 베타 시작이 5주차 말로 앞당겨져 섭외가 급하다 | 1주차부터 섭외 |
| 4 | 시험 데이터 3건 이상(개인정보 가림) | G1 시험의 기반 | 1주차 안에 확보 |
| 5 | 직접시공계획서 양식 수령 | 서류 템플릿 추가(없으면 업로드 첨부) | 3주차 전까지 |
| 6 | 현재 작성 시간·보완 횟수 측정 | 5분 달성률·감소율의 기준값 | 베타 전에 같은 공사로 측정 |

## 10. Claude Code 작업 방식 (1명, Claude Code로만 작성)

코드는 모두 Claude Code가 쓰고, 개발자는 지시·확인·판단을 맡는다. 일정 8주는 아래 방식을 지키는 것을 전제로 한다.

### 10.1 저장소 준비 (1주차 첫날)

- 프로젝트 저장소를 만들고, 루트에 `CLAUDE.md`를 둔다. 담을 내용: 문서 위치(PRD·SRS·VPS), 시험 실행 명령, 코딩 규칙, "SRS의 SR 번호를 기준으로 작업하고 시험이 통과해야 완료", "개인정보·API 키를 저장소에 넣지 않는다".
- 시험 데이터는 개인정보를 가려서 `testdata/`에 둔다. API 키 등 비밀값은 환경 변수로만 쓴다.
- 문서(SRS·PRD)를 저장소 `docs/`에 복사해 두어 Claude Code가 바로 읽을 수 있게 한다.

### 10.2 작업 단위와 지시 방식

| 원칙 | 방법 |
| --- | --- |
| 작은 단위로 지시 | 한 번에 SR 3~8개(한 영역 단위). 예: "SR-SC-05, SR-PG-01~03을 구현하고 T-04, T-07이 통과하게" |
| 시험 먼저 | 먼저 시험을 만들게 하고(실패 확인), 그다음 구현 |
| 문서가 기준 | 지시에 SR·T 번호를 쓴다. 요구가 모호하면 SRS 11장 D 항목을 먼저 확인 |
| 한 세션에 한 영역 | 영역(입력, 계산, 서류, 출력, 용역비, 보안)마다 세션을 나누고, 끝나면 시험 결과와 변경 요약을 남긴다 |
| 계산 로직은 사람이 값으로 검증 | 기준 수치(622,764,021원 등)는 개발자가 직접 맞는지 확인 |

### 10.3 Claude Code로만 작성할 때 주의할 점

| 위험 | 대응 |
| --- | --- |
| Claude Code가 Excel(Windows)을 직접 열어 확인할 수 없다 | LibreOffice를 설치해 명령줄(headless)로 수식 오류를 자동 확인하고, Excel에서 여는 확인은 관문 G2·G4에서 개발자가 직접 한다 |
| 생성한 PDF·xlsx의 모양은 눈으로 봐야 안다 | 출력물 이미지 변환 후 확인하거나, 개발자가 관문마다 직접 열어 본다 |
| 시험이 통과하도록 시험을 고치는 문제 | 기준 수치 시험(golden test)은 개발자 승인 없이 수정하지 않는다고 `CLAUDE.md`에 적는다 |
| 개인정보가 든 파일이 대화에 섞임 | 시험 데이터는 개인정보를 가려서만 쓰고, 실제 업체 자료는 베타에서 운영 환경에서만 다룬다 |
| 긴 작업에서 이전 결정을 잊음 | 결정은 SRS 11장과 `CLAUDE.md`에 기록하고, 세션 시작 때 읽게 한다 |
| 보안 코드(암호화·권한)의 품질 | 5주차에 보안 점검 전용 세션을 두고 SR-NF-12~18 시험(T-24, T-27, T-36, T-40, T-41)을 직접 확인 |

### 10.4 개발자가 직접 해야 하는 일 (Claude Code가 못 하는 일)

- 베타 업체 섭외, 업체 자료 수령, 직접시공계획서 양식 수령
- 호스팅·Supabase 프로젝트 생성과 접속, 도메인 준비
- Excel(Windows)에서 출력물 열어 보기, 출력물 육안 확인
- 관문 G1~G4의 통과 판단, 기준 수치 검토
- 현재 작성 시간·보완 횟수 측정, 베타 결과 기록

## 11. 올케어솔루션 홈페이지 메뉴 연결(1차 출시 뒤, 이 8주에 포함하지 않음)

올케어솔루션 홈페이지(단말기 렌탈·내역 신청 전용)에는 올케어안전플랫폼(안전보건관리계획서, 별도 회원가입·결제)과 이 프로그램(착공계 작성)을 메뉴로만 단다. 서비스마다 별도로 운영하므로 계정·결제·데이터를 합치는 통합 작업은 없다.

- **홈페이지 쪽 작업(1차 출시 뒤):** '착공계 작성' 메뉴를 추가하고 이 서비스의 주소로 연결한다.
- **이 계획에서 해 둘 일:** 서비스 주소(도메인) 준비, 링크로 들어와도 자체 관리자 로그인을 요구하는지 확인(T-44), 다른 서비스의 코드·테이블·계정에 의존하지 않기.

### 11.1 구성: NHN 서버(앱) + Supabase(로그인·데이터·파일)

| 부분 | 어디에 | 하는 일 |
| --- | --- | --- |
| 웹 프로그램(Next.js) | 올케어안전플랫폼과 같은 NHN 서버, 별도 포트(3001 등)·별도 주소 | 화면, 계산, 서류·xlsx·PDF 생성 |
| 로그인(Supabase Auth) | Supabase 클라우드(새 프로젝트, 서울 리전 권장) | 관리자 계정 로그인 |
| 데이터베이스(Supabase Postgres) | 같은 Supabase 프로젝트 | 공사·공정·용역비 등 데이터, 접근 정책(RLS)으로 관리자만 접근 |
| 파일 저장(Supabase Storage) | 같은 Supabase 프로젝트 | 내역서·사진·첨부 PDF, 결과 파일 |

**배포 방식은 올케어안전플랫폼과 같다.** GitHub 저장소를 서버에 `git clone`하고, 코드를 바꿀 때마다 서버에서 `git pull` → `npm ci` → `npm run build` → PM2 재시작을 실행한다(올케어안전플랫폼 `DEPLOY.md`와 같은 절차). 방화벽 때문에 NHN 서버는 회사 컴퓨터에서만 SSH로 접속되므로 GitHub에서 자동 배포는 못 하고 수동으로 한다. Supabase의 접속 주소와 키는 서버의 환경변수 파일(`.env.production`)에만 넣고 GitHub에는 올리지 않는다.

**서버를 같이 쓸 때 정해야 할 것**
- **포트:** 올케어안전플랫폼이 3000번을 쓴다. 착공계는 3001 같은 다른 번호로 띄우고 Nginx에서 주소별로 나눈다.
- **Nginx 업로드 한도:** 올케어안전플랫폼 설정은 업로드를 20MB로 제한한다. 착공계는 사진·PDF가 크므로 착공계 전용 설정에서 한도를 늘려야 한다(합본 PDF 100MB, 공사 1건 500MB).
- **메모리·CPU:** 올케어안전플랫폼은 PM2가 메모리 500MB를 넘으면 재시작한다. 착공계는 800행 계산과 PDF·xlsx 생성에 메모리를 쓰므로 남는 메모리를 접속해서 확인해야 한다.
- **HTTPS:** 새 주소에 Let's Encrypt 인증서를 따로 발급한다(`certbot`).

**Supabase 비용(무료로 시작, 확정)**
- 무료 요금제는 데이터베이스 500MB, 파일 저장 1GB 제한이 있고, 1주일 동안 접속이 없으면 프로젝트가 일시 중지된다(Supabase 공식 요금 안내 기준). 공사 1건이 최대 500MB라서 무료로는 몇 건 못 쓴다.
- 유료(Pro)는 월 25달러 수준(조직당)이며 파일 저장 100GB, 일 1회 백업 7일 보관이 포함된다. 요금은 바뀔 수 있으니 Supabase 요금 페이지에서 직접 확인한다.
- 무료로 시작하고, 한도(데이터베이스 500MB, 파일 1GB)에 가까워지면 유료 전환을 판단한다. 무료는 자동 백업이 없으므로 서버에서 일 1회 데이터베이스 백업과 파일 복사를 직접 마련한다(6장 위험 참고).
- 올케어안전플랫폼이 이미 Supabase 유료 조직을 쓴다면, 유료 전환 때 같은 조직에 프로젝트를 추가하는 방식이 가능한지 그때 확인한다.

### 11.2 서브도메인 만드는 방법(후이즈)

서브도메인은 이미 가진 도메인(allcaresolution.net)에 이름을 하나 더 붙이는 것이라 새로 사지 않고 **후이즈에서 DNS 레코드 한 줄을 추가**하면 된다. 후이즈 화면의 정확한 메뉴 이름은 확인하지 못했으므로 아래는 일반적인 순서다.

1. 후이즈에 로그인해 allcaresolution.net 도메인의 **DNS(네임서버·레코드) 관리** 메뉴로 들어간다.
2. 먼저 이 도메인의 **네임서버가 어디인지** 확인한다. 후이즈 네임서버를 쓰고 있으면 후이즈에서, 다른 곳(예: NHN Cloud DNS 등)을 쓰고 있으면 그곳에서 레코드를 추가해야 한다.
3. 레코드를 추가한다: 종류 **A**, 호스트(이름) 칸에 `chakgong`(그러면 주소는 `chakgong.allcaresolution.net`), 값에 **NHN 서버의 공인 IP**를 넣는다. 올케어안전플랫폼의 주소가 이미 같은 서버를 가리키고 있다면 그 IP와 같은 값이다.
4. 같은 이름의 레코드(CNAME 등)가 이미 있으면 충돌하므로 먼저 확인한다.
5. 저장 후 반영까지 보통 1시간 안팎(최대 48시간)이 걸린다.
6. 서버에서 Nginx에 새 주소(`server_name`)를 추가하고 `certbot`으로 HTTPS 인증서를 발급한다. 올케어솔루션 홈페이지가 '착공계 작성' 메뉴에서 이 주소로 연결한다.

- **스택 후보(1주차 확정 전 시험):** 테스트 vitest, xlsx 읽기·쓰기(수식 유지) exceljs 등, PDF 합본 pdf-lib 등. 2주차에 작은 표로 시험한 뒤 정한다.
