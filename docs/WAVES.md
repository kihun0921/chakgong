# 개발 Wave 계획

기준: `docs/SRS.md`(SR 116개, 시험 T-01~T-45), `docs/PRD.md`(AC 36개), `docs/개발착수계획.md`(8주).
Wave는 "끝나면 눈으로 확인하고 다음으로 넘어갈 수 있는 덩어리"다. 한 Wave는 아래 순서로 진행한다.

1. **시험 먼저** — 해당 Wave의 시험(T 번호)을 먼저 만들어 실패하는 것을 확인한다.
2. **구현** — SR 번호 단위로 만들고 시험을 통과시킨다.
3. **사람 확인** — "확인할 것"을 개발자가 직접 본다(특히 기준 수치, 출력 파일, 화면).
4. **관문 통과** — 모든 시험 통과 + 사람 확인이 끝나야 다음 Wave로 간다.

기준 수치 시험(golden test)은 개발자 승인 없이 수정하지 않는다.

| Wave | 이름 | 기간(추정) | 주요 SR | 시험 | 관문 |
| --- | --- | --- | --- | --- | --- |
| 0 | 기반 | 3일 (1주차) | - | (시험 도구 점검) | 아래 0 |
| 1 | 입력·계산 코어 | 1주차 중반~2주차 | SR-IN, SR-SC, SR-PG, SR-RS, SR-VR-01~03·05·07 | T-01~T-12, T-16, T-17 | **G1** |
| 2 | 서류·합본·교차검증 | 3주차 | SR-CM, SR-VR-04·06·08, SR-OUT-04·05 | T-13~T-15, T-18, T-21 | - |
| 3 | 출력·납품 이력 | 4주차 | SR-OUT-01~03·06~08 | T-19, T-20 | **G2** |
| 4 | 로그인·공사·기준정보·보안 | 5주차 | SR-PL, SR-DM, SR-NF-12~18 | T-22~T-27, T-41, T-44 | **G3 (베타 시작)** |
| 5 | 용역비·대시보드 | 6주차 | SR-FEE, SR-ADM | T-28~T-40, T-43 | - |
| 6 | 품질·알림·배포 | 7주차 | SR-NF-01~11, 19~31 | T-37~T-40, T-42, T-43 | - |

Wave 5·6은 베타와 병행한다(베타는 G3 통과 후 시작). Wave 1~3에서는 DB·로그인 없이 **순수 함수(`src/domain/`) + 파일 입출력**으로 만든다.

**나중으로 미룬 일 (개발자 결정, 2026-10-17):** Supabase 프로젝트 생성, 후이즈 `chakgong` A 레코드 추가, GitHub 저장소 연결은 **배포 전 또는 프로그램 완료 후 맨 나중에** 한다. 그래서 개발 중에는 아래 방식으로 간다.
- Wave 4의 로그인·공사 저장·파일 저장은 `src/lib/ports/`의 **인터페이스(로그인, 공사 저장소, 파일 저장소)** 뒤에 두고, 개발 중에는 **로컬 구현(파일·메모리)** 으로 동작시킨다.
- 배포 직전(Wave 6 끝)에 같은 인터페이스를 Supabase 구현으로 바꿔 끼운다. 화면·계산·서류 코드는 바뀌지 않아야 한다.
- 따라서 Supabase에 의존하는 항목(접근 정책 RLS, 서울 리전 보관, 무료 한도·백업, Auth 세션)의 시험은 **Supabase 연결 단계에서 다시 실행**한다. 이 전까지의 G3는 "로컬 구현으로 통과"이며, 최종 G4 전에 Supabase 구현으로 재통과해야 한다.
- 나라장터 API(SR-IN-01·02·07)는 API 키가 필요하므로 키를 받기 전까지는 파일 첨부 경로(내역서 업로드)만 먼저 만들고, API 호출은 키를 넣은 뒤 마지막에 연결한다.
